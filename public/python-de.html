Python in glpython

Was anders ist als in CPython, dem Python von python.org.

glpython führt Python 3.12 im Browser aus, mit Pyodide 0.26: das ist CPython, übersetzt nach WebAssembly. Die Sprache und die Standardbibliothek sind dieselben. Anders ist, was ein Browser nicht kann, und einiges, das glpython dazugibt. Zur Sprache selbst: das Python-Tutorial und die Sprachreferenz (beide englisch).

Dateien

  • Die Dateien des Projekts liegen im Ordner /, z. B. /main.py. import hilfe findet hilfe.py.
  • Das Arbeitsverzeichnis ist aber /home/pyodide: open("daten.txt") findet eine Datei des Projekts nicht, open("/daten.txt") schon.
  • Was ein Programm in eine Datei schreibt, bleibt nur im Speicher, bis Python neu startet (Stopp, «Python neu starten», die Seite neu laden). Es erscheint nicht im Editor und wird nicht gespeichert. Schreibt ein Programm in eine Datei des Projekts, gilt beim nächsten ▶ wieder der Text aus dem Editor.
  • ▶ führt die Hauptdatei des Projekts aus; die Konsole nennt sie.

Was im Browser fehlt

  • Kein Netz: urllib.request kennt https nicht, eine Verbindung mit socket endet mit einer Zeitüberschreitung.
  • Keine Threads und Prozesse: threading.Thread(…).start() gibt RuntimeError, subprocess, multiprocessing und os.fork() geben OSError.
  • Nur die Standardbibliothek: Es gibt kein pip; Pakete wie numpy oder requests fehlen. Aus der Standardbibliothek fehlen tkinter, turtle, sqlite3, ssl, lzma, curses, readline, dbm, venv, ensurepip und idlelib.
  • asyncio.run() geht nicht («cannot be called from a running event loop»), ebenso webbrowser.

Eingabe und Ausgabe

  • input() fragt in der Konsole: Die Zeile >>> wird zur Eingabezeile. Das geht nur, wo die Seite auf eine Antwort warten kann: in der IDE immer, in einem eingebetteten Editor (z. B. in einem Kurs) oft nicht. Dort endet input() mit RuntimeError: input() is not available here, und auch help(), breakpoint() und sys.stdin gehen dort nicht. Stopp, während das Programm wartet, gibt EOFError, wie Ctrl+D.
  • Die Ausgabe erscheint zeilenweise: Text ohne Zeilenende (print(…, end="")) erst mit der nächsten Zeile. Leere Zeilen und Leerzeichen am Anfang und am Ende der Ausgabe fallen weg (am Anfang nur, wenn das Programm ohne Fehler endet). sys.stdout und sys.stderr erscheinen zusammen in der Konsole.
  • time.sleep() wartet wirklich; was davor gedruckt wurde, steht schon da.
  • sys.exit() und exit() beenden das Programm, aber mit SystemExit in der Konsole; CPython beendet es still.
  • Eine Endlosschleife hält man mit Stopp an. Stopp beendet Python ganz, ohne KeyboardInterrupt: Danach kennt die Eingabezeile nichts mehr von vorher.

Ein Python für die ganze Sitzung

  • CPython startet für jedes python main.py neu. glpython startet Python einmal und führt bei ▶ die Hauptdatei in einem frischen Modul __main__ aus; die Dateien des Projekts werden dabei neu geladen.
  • Die Module der Standardbibliothek bleiben geladen: random setzt seine Folge fort, statt neu zu beginnen, und was ein Programm an einem solchen Modul ändert, gilt beim nächsten ▶ noch.
  • Die Eingabezeile >>> arbeitet nach ▶ mit den Variablen und Funktionen der Datei weiter, wie python -i main.py.
  • sys.argv ist [''], __file__ ist /main.py, sys.platform ist emscripten. Die Zeitzone ist die des Browsers, die Locale en_US.UTF-8.

Fehlermeldungen

  • Ein Traceback sieht aus wie in CPython. Dateien des Projekts heissen darin main.py, ohne Ordner; die Standardbibliothek /lib/python312.zip/….
  • Bei einigen häufigen Fehlern steht unter Pythons Meldung ein kurzer Hinweis, was die Ursache sein könnte. Pythons eigene Meldung bleibt unverändert.
  • Fehlernummern sind die von Emscripten: Eine fehlende Datei gibt [Errno 44] statt [Errno 2].

Turtle-Grafik

  • Statt turtle gibt es das Modul gturtle mit makeTurtle(), forward(), backward(), left(), right(), penUp(), penDown(), setPenColor(), setLineWidth() und clear().
  • Die Turtle zeichnet nicht Strich für Strich: Das Bild erscheint, wenn das Programm fertig ist (im Visualisierer Schritt für Schritt).

Tests

  • «Tests» führt die Beispiele in den Docstrings aus wie python -m doctest main.py: Die Datei wird als Modul geladen, ein Block if __name__ == "__main__": läuft nicht.
  • Anders als doctest zählt der Wert, wenn die Erwartung und die Ausgabe je ein Python-Literal sind (Zahl, Text, Liste, Tupel, Dictionary, Menge, True/False/None): 4 passt zu 4.0, "+" zu '+', [1,2,3] zu [1, 2, 3]. Alles andere (mehrere Zeilen, Fehler, Beispiele mit Optionen wie ELLIPSIS) vergleicht doctest als Text, wie gewohnt.
  • Wo eingeschaltet, nennt der Bericht auch die Zeilen, die kein Beispiel ausgeführt hat.

Der Visualisierer

Der Visualisierer führt das Programm in einem eigenen Interpreter aus, Ausdruck für Ausdruck. Das Ergebnis ist dasselbe wie in CPython; welche Schritte er zeigt, legt glpython fest:

  • Ein Name in xs[1] ist kein eigener Schritt: xs[1] wird in einem Schritt zum Element.
  • Eine Liste, ein Tupel, eine Menge oder ein Dictionary in Klammern ([…], (…), {…}) hat keinen eigenen Schritt, ausser ihr Wert sieht anders aus als der Text; eine negative Zahl wie -3 ebenso.
  • Werte stehen so da, wie man sie schreibt: Typen als int, nicht <class 'int'>. Lange Werte sind gekürzt ([1, 2, 3, 4, 5, …, 100]); ein Klick zeigt sie ganz. Was das Programm druckt, bleibt Pythons repr.
  • Was der Visualisierer nicht im Einzelnen kennt, läuft in einem einzigen Schritt.
  • Er zeigt höchstens 6000 Schritte und 200 verschachtelte Aufrufe; danach RecursionError: maximum interpreted recursion depth exceeded (CPython erlaubt etwa 1000).
  • Eine Eingabe der Konsole visualisieren heisst: die Sitzung noch einmal ablaufen lassen. Kommt dabei etwas anderes heraus (z. B. mit Zufallszahlen) oder braucht sie input(), steht ein Hinweis da statt der Visualisierung.
